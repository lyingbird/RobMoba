## 一、当前规模 vs 目标规模

### 1.1 数字对比

| 维度 | 当前 (4英雄) | 目标 (30+英雄) | 增长倍数 |
|------|-------------|---------------|----------|
| 英雄数 | 4 (+1测试) | 30~40 | **7.5~10x** |

| SkillConfig 行数 | 179 行 | ~1200+ 行 | **6.7x** |
| 每个英雄 touch points | 7 处 | 7 处 (不变) | — |

### 1.2 当前"加一个英雄"的完整 touch points

| # | 操作 | 文件 | 行数 |
|---|------|------|------|
| 1 | **新建** 3 个技能文件 | `Skills/Skill_XXXX.lua × 3` | ~150-250行/技能 |
| 2 | **追加** 3 条技能数据 | `SkillConfig.lua` | ~30行 |
| 3 | **追加** 1 个英雄块 | `HeroConfig.lua` | ~40行 |

| 7 | **可能** 需要过场动画数据 | `CinematicData/XXXCinematic.lua` | 不定 |

**问题：加 30 个英雄 = 重复执行这个流程 30 次，错一个地方就出 bug。**

## 二、五大核心问题与解决方案

### 🔴 问题 1: 英雄列表硬编码散落 — "忘改一处就炸"

**现状分析**：

英雄列表在 **至少 3 处** 独立维护：

```lua
-- UI_HeroSelect.lua:34 (客户端)
local HERO_ORDER = { "Angela", "Lux", "HouYi", "LianPo", "Test" }

-- GameManager.server.lua:79 (服务端)
local DEFAULT_HEROES = { "Angela", "Lux", "HouYi", "LianPo" }

-- HeroConfig.lua (ReplicatedStorage, 共享)
-- 这里是 source of truth, 但上面两处不引用它
```

30 英雄时：加一个英雄要改 3 处，忘改 `DEFAULT_HEROES` → 服务端不认，忘改 `HERO_ORDER` → 选人界面看不到。

**解决方案：HeroConfig 成为唯一 Source of Truth**

```lua
-- HeroConfig.lua (新增字段)
["Angela"] = {
    HeroID = "Angela",
    DisplayName = "安琪拉",
    SortOrder = 1,                  -- ← 新增：控制选人界面排序
    Enabled = true,                 -- ← 新增：是否启用（可用于灰度发布）
    Role = "Mage",                  -- ← 新增：职业分类 (Mage/Marksman/Tank/Assassin/Support/Fighter)
    Difficulty = 2,                 -- ← 新增：难度星级 (1-3, 用于新手推荐)
    Tags = { "Burst", "Control" },  -- ← 新增：特性标签
    FreeRotation = true,            -- ← 新增：是否在免费轮换中
    ...
},

-- UI_HeroSelect.lua (改为自动派生)
local HeroConfig = require(ReplicatedStorage.HeroConfig)
local HERO_ORDER = {}
for key, data in pairs(HeroConfig) do
    if data.Enabled ~= false then
        table.insert(HERO_ORDER, key)
    end
end
table.sort(HERO_ORDER, function(a, b)
    return (HeroConfig[a].SortOrder or 999) < (HeroConfig[b].SortOrder or 999)
end)

-- GameManager.server.lua (同样自动派生)
local HeroConfig = require(ReplicatedStorage.HeroConfig)
local DEFAULT_HEROES = {}
for key, data in pairs(HeroConfig) do
    if data.Enabled ~= false and key ~= "Test" then
        table.insert(DEFAULT_HEROES, key)
    end
end
```

**效果：加一个英雄只需要在 HeroConfig 里写一次，其他地方自动识别。**

### 🔴 问题 2: 大配置文件可维护性 — "1200 行的 Config 谁敢改"

**现状分析**：

| 文件 | 当前行数 | 30英雄预估 | 问题 |
|------|----------|-----------|------|
| HeroConfig.lua | 172 | ~1200 | 每英雄 ~40行含 Poses 矩阵 |

| EffectConfig.lua (新) | — | ~800 | 每效果 ~8行 × 100+ 效果 |

**解决方案：按英雄拆分配置 + 注册表汇聚模式**

```

  ├── Heroes/                       # ← 新目录：每英雄一个文件
  │   ├── Angela.lua                #   ~50行 (英雄配置 + 技能ID映射)
  │   ├── Lux.lua
  │   ├── HouYi.lua
  │   ├── LianPo.lua
  │   ├── ZhaoYun.lua              # 未来新英雄
  │   └── ...
  ├── SkillRegistry.lua             # 汇聚器：按英雄分组的技能配置
  ├── Skills/                       # ← 新目录：按英雄分组
  │   ├── Angela_Skills.lua         #   安琪拉的3个技能配置
  │   ├── Lux_Skills.lua
  │   └── ...
  └── EffectConfig.lua              # 效果配置（共享，不按英雄拆分）
```

**HeroRegistry.lua — 自动发现模式**：

```lua
-- HeroRegistry.lua
-- 自动扫描 Heroes/ 目录下所有 ModuleScript, 汇聚为统一配置表
local Heroes = script.Parent.Heroes
local registry = {}

for _, module in ipairs(Heroes:GetChildren()) do
    if module:IsA("ModuleScript") then
        local heroData = require(module)
        registry[heroData.HeroID] = heroData
    end
end

return registry
```

### 🟡 问题 3: 技能实现的模式沉淀 — "100个技能不能写100种写法"

**现状分析**：

通过分析现有 15 个技能，可以归纳出 **7 种基础技能模式**（archetype）：

| 模式 | 当前技能示例 | 核心逻辑 | HOK 对应 |
|------|------------|----------|----------|
| **Projectile** (直线弹道) | Fireball, LuxQ, AngelaQ | 创建弹体→飞行→碰撞检测→命中效果 | 射手普攻, 指向技能 |
| **AreaDrop** (落地AOE) | LuxE, HouYiW | 弹体飞到目标位→创建持续区域→Tick | 区域技能 |
| **Beam** (激光) | LuxR, AngelaR | 无弹体→即时/持续直线判定 | 直线贯穿技能 |
| **Shield** (护盾) | LuxW, LianPoW | 给自身/队友添加ForceField + Attribute | 护盾类 |
| **Dash** (冲刺) | LianPoQ | 移动自身到目标位→路径上碰撞检测 | 突进类 |
| **SelfBuff** (自增益) | HouYiQ | 增强普攻/临时属性→持续N秒 | 自我强化 |
| **GroundSlam** (地面AOE) | LianPoR, LianPoCinematic | 即时范围判定→多段伤害 | 范围技能 |

**问题**：这些模式没有被抽象成可复用的中间层。每个 Skill_XXXX.lua 都从零写弹道/碰撞/区域逻辑。

**解决方案：技能 Archetype 中间层**

```
BaseSkill (基类: CD/符文/Recast)
  ├── ProjectileSkill (弹道基类)
  │   ├── 提供: 创建弹体、飞行驱动、碰撞检测、命中回调
  │   ├── 子类只需重写: GetProjectileConfig() + OnProjectileHit()
  │   └── 覆盖率: ~40% 的技能 (直线弹道最常见)
  │
  ├── AreaSkill (区域基类)
  │   ├── 提供: 创建区域、Tick循环、范围检测、过期清理
  │   ├── 子类只需重写: GetAreaConfig() + OnAreaTick() + OnAreaExpire()
  │   └── 覆盖率: ~25% 的技能
  │
  ├── DashSkill (冲刺基类)
  │   ├── 提供: 位移驱动、路径碰撞、到达回调
  │   ├── 子类只需重写: GetDashConfig() + OnDashHit() + OnDashEnd()
  │   └── 覆盖率: ~15% 的技能
  │
  ├── BeamSkill (激光基类)
  │   ├── 提供: 直线判定、持续/瞬时模式
  │   └── 覆盖率: ~10% 的技能
  │
  └── InstantSkill (瞬发基类)
      ├── 提供: 立即执行效果 (护盾/Buff/自增强)
      └── 覆盖率: ~10% 的技能
```

**示例 — ProjectileSkill 基类**：

```lua
-- ProjectileSkill.lua (新增中间层)
local BaseSkill = require(...)
local CombatUtils = require(...)
local BuffSystem = require(...)

local ProjectileSkill = setmetatable({}, BaseSkill)
ProjectileSkill.__index = ProjectileSkill

function ProjectileSkill:OnCast(player, targetPos)
    local config = self:GetProjectileConfig()
    local origin = player.Character.HumanoidRootPart.Position
    local direction = (targetPos - origin).Unit

    -- 创建弹体 (通用逻辑)
    local bullet = self:CreateBullet(origin, config)
    bullet.AssemblyLinearVelocity = direction * config.Speed

    -- 碰撞检测 (通用逻辑)
    local hitConn
    hitConn = bullet.Touched:Connect(function(hit)
        -- ... 通用碰撞过滤、敌我判断 ...
        if isValidTarget then
            hitConn:Disconnect()
            self:OnProjectileHit(player, target, bullet.Position)
            -- 自动应用配置的效果
            for _, effectId in ipairs(config.OnHitEffects or {}) do
                BuffSystem:ApplyEffect(player.Character, target, effectId)
            end
            bullet:Destroy()
        end
    end)

    -- 超时清理 (通用逻辑)
    task.delay(config.MaxLifetime or 3, function()
        if bullet.Parent then bullet:Destroy() end
    end)
end

-- 子类必须重写
function ProjectileSkill:GetProjectileConfig()
    error("子类必须实现 GetProjectileConfig()")
end

-- 子类可选重写 (默认空操作)
function ProjectileSkill:OnProjectileHit(player, target, hitPos)
end

return ProjectileSkill
```

**子类简化后 — Skill_1002 LuxQ**：

```lua
-- 重构前: ~210 行, 内联弹道+碰撞+束缚逻辑
-- 重构后: ~40 行
local ProjectileSkill = require(...)

local LuxQ = setmetatable({}, ProjectileSkill)
LuxQ.__index = LuxQ

function LuxQ:GetProjectileConfig()
    return {
        Speed = 55,
        Size = Vector3.new(2, 2, 4),
        Color = Color3.fromRGB(255, 255, 200),
        Material = Enum.Material.Neon,
        MaxPierceCount = 2,           -- LuxQ 特色：可穿透 2 个目标
        OnHitEffects = { 3020, 3021 }, -- 伤害 + 束缚
    }
end

function LuxQ:OnProjectileHit(player, target, hitPos)
    -- LuxQ 独特逻辑：被束缚目标头顶显示标记
    SkillPresenter:PlayEffect(target, "root_mark")
end

return LuxQ
```

**这对 30+ 英雄的意义**：
- 新弹道类技能：继承 `ProjectileSkill`，写 ~40 行 vs 现在的 ~200 行
- 通用 bug 修一次影响所有弹道技能（如碰撞检测优化）
- 策划看 `GetProjectileConfig()` 就知道能调什么参数

### 🟡 问题 5: 技能查找性能 — "100个文件的 FindFirstChild"

**现状分析**：

```lua
-- PlayerSkillManager.server.lua:75
local skillModule = ServerScriptService.ServerModules.Skills:FindFirstChild("Skill_" .. skillID)
```

每次装备技能都做字符串拼接 + 树搜索。100+ 文件时虽然 Roblox 内部可能有优化，但不确定。

**解决方案：启动时建立一次性查找表**

```lua
-- PlayerSkillManager.server.lua 顶部
local SkillModuleMap = {}
for _, mod in ipairs(ServerScriptService.ServerModules.Skills:GetChildren()) do
    if mod:IsA("ModuleScript") then
        local id = tonumber(mod.Name:match("Skill_(%d+)"))
        if id then
            SkillModuleMap[id] = mod
        end
    end
end

-- 使用时 O(1) 查找
local function getSkillModule(skillID)
    return SkillModuleMap[skillID]
end
```

## 四、"新英雄接入清单" — 标准化流程

```
        ├── 填写技能槽映射 (Skills = { Q=1016, W=1017, R=1018 })
        ├── 填写属性数值 (BaseStats + GrowthStats)
        └── 填写动画姿态 (Poses/CastDurations/MoveLock)

        ├── 填写 3 个技能的标准字段 (CD/Range/CastRule/Speed)

Step 3: 在 EffectConfig.lua 中添加赵云专属效果
        └── 如果效果类型已有 (如减速/伤害), 复用通用效果或微调参数

Step 4: (可选) 在 PassiveConfig.lua 中添加被动定义
```

### 4.2 程序侧（写逻辑）

```
Step 5: 判断技能 Archetype
        ├── Q: 冲刺 → 继承 DashSkill
        ├── W: 范围AOE → 继承 AreaSkill

```

## 五、效果复用性分析 — 30 英雄的效果池

### 5.1 王者荣耀技能效果类型分布

基于 HOK 22.技能效果组合表 和当前 15 个技能的分析，30+ 英雄的效果可以归类为：

| 效果类型 | 预估占比 | 典型效果 | 复用度 |
|----------|---------|---------|--------|
| **Damage** | 35% | 固定伤害/百分比伤害/真实伤害 | 中（数值不同，结构相同）|
| **CC** | 20% | 眩晕/减速/定身/击飞/沉默/缴械 | **高**（6种CC类型覆盖 90%）|
| **Shield** | 10% | 固定值护盾/百分比护盾 | **高** |
| **StatMod** | 15% | 攻速/移速/护甲/法抗增减 | **高**（同结构不同参数）|
| **DoT/HoT** | 10% | 灼烧/中毒/回复 | **高** |
| **Special** | 10% | 复活/隐身/变身/牵引 | **低**（需特殊代码）|

**结论**：约 **70-80% 的效果** 可以通过 EffectConfig 的 6 种类型 + 参数化覆盖，只有 ~20% 需要特殊逻辑。

## 七、关键设计决策记录

| 决策 | 选项 A | 选项 B | **选择** | 理由 |
|------|--------|--------|----------|------|
| 配置拆分粒度 | 按英雄拆分 | 按类型拆分(所有技能一个文件) | **按英雄** | 加英雄时改动集中，利于并行开发 |
| 注册机制 | 手动注册表 | 自动目录扫描 | **自动扫描** | 零遗漏，加文件即生效 |
| 技能中间层 | 无中间层(BaseSkill直接继承) | Archetype 中间层 | **Archetype** | 30+ 英雄时代码复用率 60%+ |
| 效果配置 | 按英雄拆分 | 全局一个文件 | **全局** | 效果复用度高，跨英雄引用频繁 |
| ID 编号方案 | 连续编号 | 分段预留 | **分段预留** | 同英雄的 ID 连续，便于维护 |
| UI 布局 | 多页切换 | Grid + 滚动 | **Grid + 滚动** | 更符合 Roblox 操作习惯 |

## 八、风险与注意事项

1. **向后兼容**：阶段 0 的拆分必须保证现有 4 英雄功能不变，建议：先创建新结构 → 迁移 → 验证 → 删旧文件
2. **Rojo 同步**：`default.project.json` 需要更新以映射新目录结构 (Heroes/, Skills/)
3. **Roblox `require()` 限制**：Roblox 的 ModuleScript require 不能动态拼路径，必须通过 Instance 引用。HeroRegistry 用 `GetChildren()` + `require()` 的模式是可行的
4. **内存**：30 个英雄的配置表全部加载到内存 ≈ 几十 KB，在 Roblox 中完全无压力
5. **技能 Archetype 继承深度**：保持 3 层以内 (BaseSkill → ArchetypeSkill → ConcreteSkill)，避免过度抽象
