## 一、HOK 配置架构深度分析

### 1.1 五表分离架构

HOK 采用 **5 张核心表 + Action 编辑器** 的架构，形成完整的技能数据管线：

```
┌─────────────────────────────────────────────────────────────────┐
│                    HOK 技能配置架构                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  11.英雄信息表 ──┐                                               │
│    (英雄级别)    │    21.技能基础表 ──┐                           │
│    6技能槽位     │──▶  (技能级别)     │    22.技能效果组合 ──┐    │
│    5被动槽位     │     施放规则       │──▶  (效果级别)       │    │
│    基础属性      │     指示器配置     │     N个效果槽        │    │
│    成长曲线      │     CD/消耗/成长   │     叠加/互斥/覆盖   │    │
│                  │     ┌─────────────┘     持续时间+成长     │    │
│  15.英雄能量表   │     │                   伤害衰减/上限     │    │
│    (能量系统)    │     │                                     │    │
│    法力/怒气/能量│     │    26.技能被动表                     │    │
│    回复/消耗规则 │     │──▶  (被动级别)                       │    │
│                  │     │     事件驱动触发                     │    │
│                  │     │     条件组合(AND/OR)                 │    │
│                  │     │     7种触发类型参数                   │    │
│                  │     │                                     │    │
│                  │     │    AGE Action Editor                │    │
│                  │     └──▶  (时间轴驱动)                     │    │
│                  │          动画/特效/碰撞/行为               │    │
│                  │          Track + Event 模型                │    │
└─────────────────┴───────────────────────────────────────────────┘
```

### 1.2 各表核心字段与设计理念

#### 11. 英雄信息表 — "英雄是技能的容器"
- **6 个技能槽位**：每槽包含 `SkillID + PassiveID + 解锁星级 + 关联技能 + 技能豆ID`
- **5 个被动技能槽**：允许英雄有多个独立被动
- **3 个初始 Buff**：出生自带的状态效果
- **属性成长体系**：基础值 + 成长值（HP/攻击/法强/护甲/魔抗/攻速/暴击率/暴击伤害）
- **设计理念**：英雄只是一个"框架"，所有能力通过 ID 引用组装

#### 21. 技能基础表 — "技能是行为的定义"（~200列）
- **核心定义**：ID、名称、槽位、类型、释放规则、筛选规则
- **数值体系**：5 组描述属性（类型 + 基础值 + 成长值），冷却 + 成长，消耗 + 成长
- **指示器系统**：标准/动态/多段/小地图 4 类指示器，各有独立配置
- **效果引用**：`自身技能效果组合ID` + `目标技能效果组合ID` → 引用 22 表
- **Action 引用**：`动作路径` → 引用 AGE 导出的 Lua 文件
- **蓄力系统**：蓄力效果ID/结束效果ID/时间上限/解除时间/CD万分比
- **设计理念**：技能只定义"做什么"和"怎么触发"，具体效果由 22 表承载

#### 22. 技能效果组合表 — "效果是数值的载体"（~300+列）
- **效果类型分层**：效果类型 → 效果子类型 → 控制类型 → 显示类型
- **N 个效果槽**（至少 3 个，每个含 19 个参数 + 19 个成长参数 + 4 个额外参数）
- **叠加体系**：叠加规则 + 叠加次数上限 + 叠加上限成长 + 清除规则
- **互斥体系**：最多 10 个互斥效果组合 ID + 4 个覆盖效果组合 ID
- **持续时间体系**：基础时长 + 成长值 + 属性缩放 + 蓄力加成 + 最大值
- **伤害控制**：伤害上限（通用/野怪/偷塔）+ 吸血衰减 + 伤害衰减（系数 + 最低）
- **前置条件**：前置效果组合 ID + 技能槽位 Mask
- **设计理念**：效果是可组合、可叠加、可互斥的独立数据单元

#### 26. 技能被动表 — "被动是事件的响应"
- **事件驱动**：被动类型（时间触发/生存期时间触发/等）+ 7 个类型参数
- **条件系统**：逻辑运算（AND/OR）+ 2 个条件（各含类型 + 10 个参数）
  - 条件类型示例：血量条件、护盾伤害条件、血量区间改变条件
- **关联性**：依赖技能ID、绑定皮肤、独立冷却
- **设计理念**：被动不是技能的特例，是独立的事件-条件-响应系统

#### 15. 英雄能量表 — "能量是施放的约束"
- **能量类型**：法力/无消耗/能量/怒气（完全不同的回复和消耗逻辑）
- **显示配置**：名称/回复文本/消耗文本/能量条资源
- **回复机制**：频率 + CDR 影响 + 成长
- **特殊状态**：零能量效果/满能量效果/半能量效果
- **设计理念**：能量不是简单的数字，是影响游戏节奏的独立子系统

### 1.3 AGE Action Editor — 时间轴驱动的技能演出

```
Action
  ├── TemplateObject[] (角色/子弹/特效对象引用)
  ├── Track: SetBehaviourMode    (行为控制)
  ├── Track: SetAttackDir        (朝向控制)
  ├── Track: ForbidAbility       (技能禁用)
  ├── Track: PlayAnimation       (动画播放)
  ├── Track: TriggerParticle     (特效触发)
  ├── Track: SpawnObject         (碰撞体生成)
  ├── Track: HitTrigger          (命中检测)
  └── Track: SkillFunc           (技能效果触发)
```

**关键事件类型**（来自 Events.xml + EventsExtension.xml）：
- **Movement**: ModifyTransform（变换操作）
- **Effect**: TriggerParticle（特效，含裁剪/绑定/缩放/层级等 40+ 参数）
- **控制类型**: 晕眩/减速/嘲讽/恐惧/冰冻/击飞/沉默/石化/定身/压制/牵引/缴械/致盲/霸体/金身...（60+ 种）
- **技能槽位**: 普攻/技能1/技能2/技能3/EX技能/恢复/召唤师技能/强化普攻/装备...

## 二、当前项目架构分析

### 2.1 文件结构

```
ReplicatedStorage/
  ├── SkillConfig.lua        # 15个技能的扁平数值表
  ├── HeroConfig.lua         # 5个英雄（技能槽映射+动画姿态+主题色）
  ├── RuneConfig.lua         # 3种符文（CDR/MultiShot/DamageBoost）
  ├── ItemConfig.lua         # 装备配置
  └── LevelConfig.lua        # 等级+属性成长

ServerScriptService/
  ├── PlayerSkillManager.server.lua    # 技能管理器（装备/施放/CD）
  └── ServerModules/
      ├── BaseSkill.lua                # 基类（CD管理+符文系统+Recast）
      ├── SkillPresenter.lua           # 演出系统（动画/VFX/音效/相机）
      ├── CombatUtils.lua              # 战斗目标工具
      └── Skills/
          ├── Skill_1001.lua ~ Skill_1015.lua   # 15个技能实现
```

### 2.2 当前架构的优劣

#### ✅ 优点
1. **简单直观**：每个技能一个文件，修改独立
2. **BaseSkill 基类**：提供了 CD 管理、符文系统、Recast 机制
3. **SkillPresenter**：已有数据驱动的演出系统（基于 SkillEditorData）
4. **CombatUtils**：独立的战斗目标工具，可复用

#### ❌ 问题
| 问题 | 严重程度 | 详情 |
|------|----------|------|
| **无效果系统** | 🔴 严重 | 减速/束缚/护盾/击飞等内联在各 Skill_XXXX 中，无法复用、无法叠加管理 |
| **无 Buff 系统** | 🔴 严重 | 持续效果靠 `task.delay` 手动管理，无叠加/互斥/覆盖逻辑 |
| **配置扁平化** | 🟡 中等 | SkillConfig 中 ad-hoc 字段（StunDuration/VortexRadius/ShieldAmount/KnockupDuration...），新技能需要发明新字段 |
| **无被动系统** | 🟡 中等 | 英雄没有被动能力，HeroConfig 中无被动槽位 |
| **无能量类型** | 🟡 中等 | 所有英雄统一消耗规则，无法实现怒气/能量等差异化 |
| **无数值成长** | 🟡 中等 | 技能数值固定，无等级成长/技能升级体系 |
| **VFX 内联** | 🟡 中等 | 每个技能自带 `createXXXVFX()` 函数，与逻辑耦合 |

## 三、重构方案

### 3.1 设计原则

> **核心思想**：借鉴 HOK 的"数据与逻辑分离"思想，但适配 Roblox Luau 生态和当前项目规模。
> **不是照搬**：HOK 的 200 列配置表是为 100+ 英雄服务的，我们 4 个英雄不需要那个复杂度。
> **渐进式重构**：分阶段推进，每阶段独立可用，不做大爆炸重构。

### 3.4 重构后的技能实现模式

当前每个 `Skill_XXXX.lua` 内联了效果逻辑，重构后变为：

```lua
-- 重构前: Skill_1013 LianPoW (258行, 大量内联效果)
function LianPoWSkill:OnCast(player, targetPos)
    -- 内联护盾逻辑 (创建ForceField, 设置Attribute, task.delay清理)
    -- 内联蓄力VFX
    -- 内联延迟AOE逻辑 (Heartbeat循环检测, 距离衰减计算)
    -- 内联减速逻辑 (修改WalkSpeed, task.delay恢复)
    -- 内联拉拽逻辑
    -- 内联Q刷新逻辑
end

-- 重构后: Skill_1013 LianPoW (~80行, 效果委托给BuffSystem)
function LianPoWSkill:OnCast(player, targetPos)
    local BuffSystem = require(BuffSystemPath)
    local config = SkillConfig[1013]
    local char = player.Character

    -- 1. 给自己加护盾 (一行代码)
    BuffSystem:ApplyEffect(char, char, config.SelfEffects[1])  -- 引用EffectConfig护盾

    -- 2. 播放蓄力演出
    SkillPresenter:PlayPresentation(player, config, targetPos)

    -- 3. 延迟AOE
    task.delay(1.0, function()
        local enemies = CombatUtils.getEnemiesInRange(player, char.HumanoidRootPart.Position, config.AreaEffects.Radius)
        for _, enemy in enemies do
            -- 应用伤害效果 + 减速效果 (各一行)
            BuffSystem:ApplyEffect(char, enemy, config.AreaEffects.HitEffects[1])
            BuffSystem:ApplyEffect(char, enemy, config.AreaEffects.HitCC[1])
        end
    end)
end
```

## 四、对比总结

| 维度 | HOK 架构 | 当前项目 | 重构目标 |
|------|----------|----------|----------|
| **表分离** | 5表 + Action Editor | 2表（Skill+Hero）| 5表（Skill+Hero+Effect+Passive+Energy）|
| **效果系统** | 效果组合表（300+列，N效果槽） | 无（内联在技能代码中） | EffectConfig + BuffSystem |
| **叠加/互斥** | 完整（叠加规则+互斥组+覆盖组） | 无 | 支持 4 种叠加 + 互斥组 |
| **被动系统** | 事件驱动 + AND/OR条件 + 7种触发 | 无 | 简化版事件-条件-效果 |
| **能量系统** | 4种类型 + 完整回复/消耗规则 | 无（所有英雄统一） | 4种基本类型 |
| **数值成长** | 基础值+成长值+属性缩放 | 无（固定数值） | 支持等级成长 + 属性加成 |
| **技能编辑器** | AGE Action Editor（专业时间轴） | SkillEditorPlugin（Studio插件） | 保持现有插件 + 增加效果引用 |
| **复杂度** | 工业级（200列/表，100+英雄） | 原型级（15个ad-hoc字段） | 适中（标准化字段 + 效果引用）|

### 关键借鉴点

1. **✅ 借鉴**: 数据与逻辑分离（效果配置独立于技能实现）
2. **✅ 借鉴**: 效果组合 + ID 引用模式（复用性）
3. **✅ 借鉴**: 叠加/互斥/覆盖规则（策划可控）
4. **✅ 借鉴**: 被动系统的事件-条件-响应模式
5. **❌ 不照搬**: HOK 的 200 列表头（我们不需要那个粒度）
6. **❌ 不照搬**: HOK 的万分比系统（保持 Lua 浮点数更直观）
7. **❌ 不照搬**: AGE 的完整 Track-Event 模型（保持我们的 SkillPresenter）

## 五、风险与注意事项

1. **向后兼容**：重构期间保持旧 SkillConfig 格式可用，新旧并行
2. **测试覆盖**：每迁移一个技能，必须 PlaySolo + 2人 LocalServer 验证
3. **性能**：BuffSystem 的 Heartbeat 循环需要注意大量 Buff 时的性能
4. **策划友好**：EffectConfig 的 ID 命名需要有规律（3000+ = 技能效果, 5000+ = 被动效果）
5. **编辑器适配**：现有 SkillEditorPlugin 需要后续更新以支持效果引用编辑
