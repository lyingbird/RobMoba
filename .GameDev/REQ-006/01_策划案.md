# 第一章 功能概述

将 15 个"各自为战"的技能实现统一到 **5 种 Archetype 基类**上，让新技能开发从"抄 200 行改 200 行"变成"继承 50 行填配置表"，同时将 SkillConfig 从 ad-hoc 字段升级为**标准化格式 + EffectConfig 引用**，消除数据重复和断裂。

## 1.1 设计目标

| 目标 | 描述 | 优先级 |
|------|------|--------|
| Archetype 中间层 | 实现 5 个技能基类（Projectile/Area/Dash/Beam/Instant），覆盖 ~90% 技能类型 | P0 |
| SkillConfig 标准化 | 统一技能配置格式：通用字段 + 效果引用 + 描述属性，消除 ad-hoc 字段 | P0 |
| 全量迁移 | 15 个现有技能全部迁移到 Archetype + 新 SkillConfig 格式 | P0 |
| BuffSystem 统一管线 | 所有技能的伤害/CC/护盾统一走 BuffSystem:ApplyEffect()，消除内联绕过 | P0 |
| BaseSkill 兼容层 | 过渡期支持新旧两种 SkillConfig 格式，不中断现有功能 | P1 |
| 玩家零感知 | 重构对玩家完全透明，技能释放行为和数值无变化 | P0 |

## 1.2 用户故事

**面向开发者（程序）**:
作为一个 **技能开发者**，
我想要 **继承一个 Archetype 基类来创建新技能，只需重写 GetConfig() 和 On...Hit() 回调**，
以便 **不再每次从零写弹道/碰撞/区域逻辑，将每个技能的代码量从 ~200 行降到 ~50-80 行**。

**面向策划**:
作为一个 **策划**，
我想要 **在 SkillConfig 中看到一个技能的所有效果引用和描述属性，格式统一可预期**，
以便 **不需要读代码就能理解技能做什么、数值改哪里**。

**面向玩家**:
作为一个 **玩家**，
我想要 **技能行为和手感完全不变**，
以便 **照常享受 RobMoba 的对战乐趣**。

## 1.3 模块拆分总览

本需求采用 **主从模式**，拆分为 3 个模块：

| 模块ID | 模块名称 | 核心内容 | 验收标准数 |
|--------|----------|----------|------------|
| MOD-A | Archetype 中间层 | 5 个 Archetype 基类 + BaseSkill 路由 | 8 条 |
| MOD-B | SkillConfig 标准化 | 新配置格式定义 + 15 技能配置迁移 | 7 条 |
| MOD-C | 技能迁移 + 兼容层 | 15 技能实现迁移 + 伤害/CC 统一走 BuffSystem | 8 条 |

### 模块关联图

```
MOD-A (Archetype 中间层)
  │   提供 5 个基类: ProjectileSkill / AreaSkill / DashSkill / BeamSkill / InstantSkill
  │

# 第二章 功能详细设计

## 2.1 MOD-A: Archetype 中间层

### 模块设计卡片

| 属性 | 值 |
|------|-----|
| 模块ID | MOD-A |
| 父需求 | REQ-006 技能框架升级 |
| 模块名称 | Archetype 中间层（5 个技能基类） |

### 2.1.1 设计理念

通过分析现有 15 个技能（来源: RESEARCH「30+英雄扩展架构方案」问题 3），归纳出 **5 种基础技能模式（Archetype）**。每个 Archetype 封装该类型技能的通用逻辑，子类只需：
1. 提供配置参数（`GetXxxConfig()`）
2. 重写特殊回调（`OnXxxHit()`、`OnXxxEnd()` 等）
3. 从 SkillConfig 读取效果引用，自动通过 BuffSystem 施加

**王者荣耀参考**: 王者荣耀的技能编辑器 AGE 也是类似思路 — 定义基础 Action 类型（弹道/区域/位移），然后通过参数化配置组合出不同技能。我们用 Luau 的 OOP 继承代替 AGE 的可视化编辑器，保持简洁。

### 2.1.2 继承层次

```
BaseSkill (既有 56 行, CD管理 + 符文系统 + Recast)
  │
  ├── ProjectileSkill (弹道基类, 新建)
  │     覆盖: 直线弹道类技能 (~40% 的技能)
  │     通用逻辑: 创建弹体 → 飞行驱动 → 碰撞检测 → 命中效果 → 超时清理
  │     子类必须: GetProjectileConfig()
  │     子类可选: OnProjectileHit() / OnProjectilePierce() / OnProjectileExpire()
  │
  ├── AreaSkill (区域基类, 新建)
  │     覆盖: 落地 AOE / 持续区域 (~25%)
  │     通用逻辑: 投放区域 → Tick 循环(Heartbeat) → 范围检测 → Tick 效果 → 过期清理
  │     子类必须: GetAreaConfig()
  │     子类可选: OnAreaTick() / OnAreaExpire() / OnAreaCreate()
  │
  ├── DashSkill (冲刺基类, 新建)
  │     覆盖: 位移突进类 (~15%)
  │     通用逻辑: TweenService 位移 → 路径碰撞(Heartbeat) → 碰撞效果 → 到达处理
  │     子类必须: GetDashConfig()
  │     子类可选: OnDashHit() / OnDashEnd() / OnDashStart()
  │
  ├── BeamSkill (激光基类, 新建)
  │     覆盖: 直线贯穿 / 持续扫射 (~10%)
  │     通用逻辑: 直线判定(Raycast/宽度检测) → 持续/瞬发模式 → 多目标命中
  │     子类必须: GetBeamConfig()
  │     子类可选: OnBeamHit() / OnBeamTick() / OnBeamEnd()
  │
  └── InstantSkill (瞬发基类, 新建)
        覆盖: 自增益 / 护盾 / 无投射物的瞬发效果 (~10%)
        通用逻辑: 立即施加效果(SelfEffects/TargetEffects) → 完成
        子类必须: GetInstantConfig()
        子类可选: OnInstantCast()
```

### 2.1.4 复合技能处理策略

部分技能横跨两个 Archetype（如 AngelaW = Projectile+Area，HouYiR = Projectile+Area 爆炸）。

**设计决策**: 以**主逻辑**确定继承的 Archetype，次要逻辑在回调中手动实现。

| 复合技能 | 主 Archetype | 次要逻辑 | 处理方式 |
|----------|-------------|----------|---------|
| AngelaW (1007) | Projectile | 命中后创建区域 | `OnProjectileHit()` 中手动创建区域+Tick |
| HouYiR (1011) | Projectile | 落点爆炸AOE | `OnProjectileHit()` 中手动做范围检测+ApplyEffect |
| LianPoW (1013) | Instant | 周围AOE伤害+减速 | `OnInstantCast()` 中手动做范围检测+ApplyEffect |

> 💡 [假设] 当前 15 个技能中的复合情况有限（3 个），用"主 Archetype + 回调扩展"模式足够。如果未来复合技能占比超过 30%，可考虑 Mixin 模式。

### 2.1.5 Archetype 基类核心接口

**所有 Archetype 共有的模式**:

```
1. 子类通过 GetXxxConfig() 提供配置
2. Archetype:OnCast() 读取配置 → 执行通用逻辑
3. 通用逻辑中在关键节点调用子类回调
4. 效果施加统一使用 BuffSystem:ApplyEffect()
5. VFX 演出统一委托给 SkillPresenter
```

**ProjectileSkill 接口规范**:

| 方法 | 必须/可选 | 说明 |
|------|----------|------|
| `GetProjectileConfig()` | 必须 | 返回 `{ Speed, Size, Color, Material, MaxLifetime, MaxPierceCount, OnHitEffects, OnHitCC }` |
| `OnProjectileHit(player, target, hitPos)` | 可选 | 命中后自定义逻辑（如 LuxQ 标记效果） |
| `OnProjectilePierce(player, target, hitPos, pierceCount)` | 可选 | 穿透时回调 |
| `OnProjectileExpire(player, lastPos)` | 可选 | 超时消失时回调 |

**AreaSkill 接口规范**:

| 方法 | 必须/可选 | 说明 |
|------|----------|------|
| `GetAreaConfig()` | 必须 | 返回 `{ Radius, Duration, TickInterval, TickEffects, OnEnterEffects, OnExpireEffects }` |
| `OnAreaTick(player, area, targets)` | 可选 | 每次 Tick 自定义逻辑 |
| `OnAreaExpire(player, area)` | 可选 | 区域消失时回调 |
| `OnAreaCreate(player, area)` | 可选 | 区域创建时回调 |

**DashSkill 接口规范**:

| 方法 | 必须/可选 | 说明 |
|------|----------|------|
| `GetDashConfig()` | 必须 | 返回 `{ Speed, Width, MaxRange, OnDashHitEffects, OnDashHitCC }` |
| `OnDashHit(player, target)` | 可选 | 路径碰撞命中回调 |
| `OnDashEnd(player, endPos)` | 可选 | 到达终点回调 |
| `OnDashStart(player, startPos)` | 可选 | 起跳前回调（如加护盾） |

**BeamSkill 接口规范**:

| 方法 | 必须/可选 | 说明 |
|------|----------|------|
| `GetBeamConfig()` | 必须 | 返回 `{ Width, Range, Duration, TickInterval, TickEffects, Mode("Instant"/"Channel") }` |
| `OnBeamHit(player, target, hitPos)` | 可选 | 命中回调 |
| `OnBeamTick(player, targets)` | 可选 | 持续模式每 Tick 回调 |
| `OnBeamEnd(player)` | 可选 | 激光结束回调 |

**InstantSkill 接口规范**:

| 方法 | 必须/可选 | 说明 |
|------|----------|------|
| `GetInstantConfig()` | 必须 | 返回 `{ SelfEffects, TargetEffects, AreaRadius(可选), AreaEffects(可选) }` |
| `OnInstantCast(player, targetPos)` | 可选 | 施放时自定义逻辑 |

### 2.1.6 BaseSkill 路由机制

现有 `BaseSkill:OnCast()` 是一个空的 warn 方法。**不改变这一设计** — 每个 Archetype 自己重写 `OnCast()`。

但需要在 `BaseSkill` 中新增一个公共方法供所有 Archetype 使用：

```
BaseSkill:ApplyEffects(source, target, effectIds)
  -- 遍历 effectIds 列表，对每个 id 调用 BuffSystem:ApplyEffect()
  -- 统一处理: 符文加成(DamageBoost)、多重施法(MultiShot)
```

这样所有 Archetype 施加效果时只需调用 `self:ApplyEffects()`，符文系统的加成逻辑在基类统一处理。

## 2.2 MOD-B: SkillConfig 标准化

### 模块设计卡片

| 属性 | 值 |
|------|-----|
| 模块ID | MOD-B |
| 父需求 | REQ-006 技能框架升级 |
| 模块名称 | SkillConfig 标准化（配置格式升级） |

### 2.2.1 设计理念

当前 SkillConfig 存在两个核心问题（来源: RESEARCH「技能配置架构分析与重构方案」阶段 2）：

| 问题 | 具体表现 | 影响 |
|------|---------|------|
| **ad-hoc 字段泛滥** | `StunDuration`/`VortexRadius`/`SwordCount`/`KnockupDuration`/`ExplosionRadius`... 每技能发明新字段 | 策划无法预期一个技能有哪些字段，新技能不知道该填什么 |
| **与 EffectConfig 断裂** | SkillConfig 中 `BaseDamage=400`，EffectConfig 中 `Amount=400`，两处定义互不引用 | 改了一处忘改另一处，数值不一致 |

**借鉴 HOK 方案**: HOK 技能基础表用"标准化通用字段 + 效果组合 ID 引用"模式。我们简化为：

```
通用字段 (所有技能都有) + Archetype 专属字段 + EffectConfig 引用 (替代 ad-hoc 字段)
```

### 2.2.2 新 SkillConfig 标准格式

```
每个技能配置条目包含 3 层字段:

Layer 1 — 通用字段 (所有技能必填):
  Name, UIName, Icon, Slot, CD, Range, CastRule, ArchetypeType

Layer 2 — Archetype 专属字段 (根据 ArchetypeType 填写):
  Projectile: Speed, Size, MaxLifetime, MaxPierceCount
  Area:       Radius, Duration, TickInterval
  Dash:       Speed, Width
  Beam:       Width, Duration, TickInterval, Mode
  Instant:    AreaRadius (可选)

Layer 3 — 效果引用 (替代所有 ad-hoc 字段):
  OnHitEffects = { effectId, ... }      -- 命中时施加
  OnHitCC = { effectId, ... }           -- 命中时控制
  SelfEffects = { effectId, ... }       -- 对自身施加
  AreaEffects = {                       -- 区域效果(可选)
    Radius, Duration, TickInterval,
    TickEffects = { effectId, ... },
    OnEnterEffects = { effectId, ... },
  }

Layer 4 — 描述属性 (用于 UI 显示, 不影响逻辑):
  DescAttrs = {
    { Type = "Damage", Label = "伤害", Value = "250", Growth = "+50/级" },
    { Type = "CC", Label = "控制", Value = "定身 1s" },
  }
```

### 2.2.3 新旧格式对比示例

**示例: LuxQ (ID:1002) — 弹道+定身**

```
旧格式 (当前):
  [1002] = {
      Name = "LuxQ", UIName = "光之束缚", Icon = "...",
      BaseCD = 11, BaseRange = 50, BaseDamage = 250,
      Speed = 55, StunDuration = 1,           ← ad-hoc
  }

新格式:
  [1002] = {
      -- Layer 1: 通用
      Name = "LuxQ", UIName = "光之束缚", Icon = "...",
      Slot = "Q",
      CD = 11,
      Range = 50,
      CastRule = "Projectile",
      ArchetypeType = "Projectile",

      -- Layer 2: Projectile 专属
      Speed = 55,
      Size = Vector3.new(2, 2, 4),
      MaxLifetime = 3,
      MaxPierceCount = 2,

      -- Layer 3: 效果引用 (替代 BaseDamage + StunDuration)
      OnHitEffects = { 3001 },    -- → EffectConfig[3001] 250伤害
      OnHitCC = { 3002 },         -- → EffectConfig[3002] 1s定身

      -- Layer 4: UI 描述
      DescAttrs = {
          { Type = "Damage", Label = "伤害", Value = "250" },
          { Type = "CC", Label = "控制", Value = "定身 1s" },
      },
  }
```

**示例: LianPoQ (ID:1012) — 冲刺+击飞**

```
旧格式:
  [1012] = {
      Name = "LianPoQ", UIName = "爆裂冲撞", Icon = "...",
      BaseCD = 8, BaseRange = 30, BaseDamage = 350,
      Speed = 40, DashWidth = 6,               ← ad-hoc
      KnockupDuration = 0.8,                   ← ad-hoc
  }

新格式:
  [1012] = {
      Name = "LianPoQ", UIName = "爆裂冲撞", Icon = "...",
      Slot = "Q", CD = 8, Range = 30,
      CastRule = "Dash", ArchetypeType = "Dash",
      Speed = 40, Width = 6,
      OnHitEffects = { 3060 },    -- → 350物理伤害
      OnHitCC = { 3061 },         -- → 0.8s击飞
      DescAttrs = {
          { Type = "Damage", Label = "伤害", Value = "350" },
          { Type = "CC", Label = "控制", Value = "击飞 0.8s" },
      },
  }
```

**示例: AngelaW (ID:1007) — 弹道+眩晕+漩涡区域 (复合)**

```
旧格式:
  [1007] = {

## 2.3 MOD-C: 技能迁移 + 兼容层

### 模块设计卡片

| 属性 | 值 |
|------|-----|
| 模块ID | MOD-C |
| 父需求 | REQ-006 技能框架升级 |
| 模块名称 | 技能迁移 + 兼容层 |

### 2.3.1 迁移策略

**核心原则: 所有伤害/CC/护盾统一走 BuffSystem 管线**

当前状况（代码探测结果）：
- 伤害: 大部分技能直接 `humanoid:TakeDamage(finalDamage)` — **绕过 BuffSystem**
- CC: 部分走 `BuffSystem:ApplyEffect()`（如 LuxQ 定身），部分自行实现（如 LianPoQ 击飞内联 28 行）
- 护盾: 走 BuffSystem（LianPoW, LuxW）

**迁移后**: 
- 伤害: 全部通过 `self:ApplyEffects(source, target, { effectId })` → BuffSystem → EffectExecutor → TakeDamage（Shield 抵消生效）
- CC: 全部通过 BuffSystem:ApplyEffect() → EffectExecutor._executeCC()
- 护盾: 保持不变（已正确走 BuffSystem）

### 2.3.2 迁移优先级与分批

**第一批（验证 Archetype 可行性，每类型 1 个代表）**:

| 技能 | Archetype | 理由 |
|------|-----------|------|
| Skill_1001 Fireball | Projectile | 最简单的弹道，纯验证骨架 |
| Skill_1004 LuxE | Area | 典型区域技能（投放+持续+引爆） |
| Skill_1012 LianPoQ | Dash | 唯一的冲刺技能 |
| Skill_1005 LuxR | Beam | 瞬发直线贯穿 |
| Skill_1013 LianPoW | Instant | 瞬发AOE+护盾 |

**第二批（同类型批量迁移）**:
- Projectile 类: 1002, 1003, 1006, 1007, 1011 (5 个)
- Area 类: 1010, 1014 (2 个)
- Beam 类: 1008 (1 个)
- Instant 类: 1009, 1015 (2 个)

### 2.3.3 单技能迁移检查清单

每个技能迁移时必须确认：

1. ✅ 继承正确的 Archetype 基类
2. ✅ `GetXxxConfig()` 返回值与 SkillConfig 新格式对齐
3. ✅ 所有伤害走 `self:ApplyEffects()` → BuffSystem，**不再直接 TakeDamage**
4. ✅ 所有 CC 走 `BuffSystem:ApplyEffect()`，**不再内联实现**
5. ✅ VFX 逻辑保持在技能文件中（本期不拆 VFX）
6. ✅ SkillPresenter 调用不变
7. ✅ Recast 机制兼容
8. ✅ 符文加成逻辑通过 BaseSkill:ApplyEffects() 统一处理

### 2.3.4 BaseSkill 兼容层设计

**兼容期**: MOD-C 迁移过程中，已迁移的技能使用新格式，未迁移的使用旧格式。BaseSkill 需兼容两者。

**兼容点**:

| 字段 | 旧格式 | 新格式 | 兼容方式 |
|------|--------|--------|---------|
| CD | `BaseCD` | `CD` | `self.Config.CD or self.Config.BaseCD` |
| 射程 | `BaseRange` | `Range` | `self.Config.Range or self.Config.BaseRange` |
| 技能类型 | 无 | `ArchetypeType` | 无则默认走旧路径 `OnCast()` |
| 效果引用 | 无 | `OnHitEffects` 等 | 无则由子类自行处理（旧行为） |

**兼容层退出条件**: 15 个技能全部迁移完成后，旧格式兼容代码可保留但标记为 `-- LEGACY: 可在 REQ-007 后删除`。

### 2.3.5 EffectExecutor 增强需求

代码探测发现 EffectExecutor 有几个限制需要在迁移中解决：

| 限制 | 影响 | 需要增强 |

| 伤害不走属性公式 | EffectConfig.Amount 是固定值 | EffectExecutor._executeDamage 需读取 `ScalesWith` 字段做属性加成计算 |
| Shield 重复检查 | Damage 和 DoT 中各自检查 Shield | 提取为公共方法 `_applyDamageAfterShield()` |

> 💡 [假设] EffectExecutor 增强作为 MOD-C 迁移的一部分执行，不单独成模块。如果工作量过大，主程可决定拆分。
